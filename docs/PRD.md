## 2. 배경 및 해결하려는 문제

기획 초안에는 해결할 문제가 비어 있었으므로, 아래 4가지를 구체적인 문제로 정의한다.

| # | 문제 | 상황 예시 | 서비스의 해법 |
|---|------|-----------|---------------|
| P1 | 결정 피로 | 점심·저녁마다 "아무거나"를 반복하며 10분 이상 고민한다. | 조건을 걸고 버튼 한 번으로 후보를 하나 뽑아준다. |
| P2 | 가고 싶던 곳을 잊어버림 | 지나가다 본 식당, 지인이 추천한 식당을 정작 고를 때는 기억하지 못한다. | "가보고 싶음" 상태로 저장하고 추천 후보에 포함한다. |
| P3 | 팀 점심 합의의 어려움 | 여러 명이 의견을 내다 보면 결론이 나지 않거나 특정인이 늘 정하게 된다. | (향후) 공유 목록에서 무작위로 뽑아 합의 비용을 줄인다. MVP는 개인용이다. |
| P4 | 같은 곳만 반복 | 익숙한 몇 곳만 가고, 최근에 갔던 곳이 또 나온다. | 최근 N일 내 방문한 곳을 제외하고, 방문 기록으로 반복 패턴을 확인한다. |

## 3. 목표와 비목표

### 3.1 목표 (MVP)
- G1. 식당을 등록·수정·삭제·조회할 수 있다.
- G2. 카테고리, 가격대, 상태, 최근 방문 제외 조건으로 무작위 추천을 받을 수 있다.
- G3. 추천 결과를 수락하면 방문 기록이 남고, 이후 추천에 반영된다.
- G4. 프론트엔드, 백엔드, DB 세 계층이 역할별로 분리되어 있고 향후 별도 서버로 이전할 수 있다.
- G5. (v0.5) 방문·넘김 이력을 추천에 반영하고(가중치), 오래 방치된 식당·카테고리를 드러내며, 월 단위로 식생활을 돌아볼 수 있다.
- G6. (v0.6) 공공데이터 상가정보 카탈로그에서 식당을 검색해 이름·주소·카테고리를 자동으로 채워 등록할 수 있다(수동 입력은 유지).

### 3.2 비목표 (MVP에서 하지 않음)
- 로그인·회원가입·권한 관리
- 팀 공유방, 투표, 다중 사용자 데이터 분리
- 지도·위치 기반 추천(좌표는 `places`에 저장만 하며 거리 계산·정렬·지도 표시는 하지 않는다)
- 외부 맛집 API(카카오 로컬 등) 연동. 런타임에 외부 서비스를 호출하지 않는다.
- 리뷰·평점의 소셜 기능, 사진 업로드
- 모바일 네이티브 앱 (반응형 웹으로만 대응)

**범위 내 명확화 (v0.6)**: 공공데이터포털에서 사용자가 직접 내려받은 「소상공인시장진흥공단_상가(상권)정보」 CSV를 백엔드 CLI로 DB에 **일회성·수동 임포트**하는 것은 범위 내다. 이는 외부 API 연동이 아니라 파일 임포트이며, 앱은 임포트 이후 외부 호출 없이 내부 DB의 `places` 테이블만 조회한다.

### 3.3 전제 (Assumption)
- **MVP는 개인 사용, 단일 사용자를 기준으로 시작한다.** 사용자 식별 없이 하나의 데이터 집합만 존재한다.
- 팀 공유와 로그인은 비목표이며 13장의 로드맵으로 둔다. 다만 확장 시 부담을 줄이기 위해 데이터 모델에 `owner_id` 등을 지금 넣지는 않고, 확장 시 마이그레이션으로 추가한다(열린 질문 참고).
- 서비스는 개발 서버 한 대에서 운영하며, 외부 공개 배포는 MVP 범위가 아니다. 내부망 또는 개인 환경에서 접근한다.
- 사용 언어는 한국어 단일이다.

## 4. 대상 사용자 및 페르소나

### 4.1 페르소나

**페르소나 A: 김민준 (32세, 개발자, 1인 가구)**
- 회사 근처 식당 10여 곳을 돌려 먹으며, 점심마다 "뭐 먹지"로 시간을 쓴다.
- 인스타그램·지인 추천으로 알게 된 식당은 메모앱에 흩어져 있어 잘 찾지 못한다.
- 니즈: 가고 싶은 곳을 한곳에 모으고, 최근에 간 곳은 빼고 뽑아주길 원한다.

**페르소나 B: 이수진 (28세, 마케터, 팀 막내)**
- 팀 점심 메뉴를 정하는 역할을 자주 맡는다. 의견이 갈리면 부담이 크다.
- 니즈: 후보 몇 곳에서 공정하게 하나를 뽑아주는 도구. MVP에서는 본인 목록으로 먼저 쓰고, 이후 팀 공유를 기대한다.

### 4.2 핵심 사용자 시나리오

| ID | 시나리오 | 흐름 |
|----|----------|------|
| S1 | 식당 저장 | 점심 후 마음에 든 식당을 등록한다: 이름, 카테고리, 가격대, 메모 입력 후 저장. |
| S2 | 가보고 싶은 곳 적립 | 추천받은 식당을 "가보고 싶음" 상태로 빠르게 등록한다(이름과 카테고리만). |
| S3 | 오늘의 추천 | 메인 화면에서 "한식, 1만원대" 조건을 켜고 [추천받기]를 누른다. 카드로 식당이 표시된다. |
| S4 | 다시 뽑기 | 마음에 들지 않으면 [다시 뽑기]를 누른다. 직전에 나온 식당은 연속으로 나오지 않는다. |
| S5 | 수락과 방문 처리 | [여기로 갈래요]를 누르면 오늘 날짜로 방문 기록이 생기고, 최근 N일 제외 조건에 반영된다. |
| S6 | 기록 확인 | 방문 기록 화면에서 최근 한 달간 어디를 갔는지 확인하고, 필요 시 기록을 삭제한다. |
| S7 | 미뤄둔 곳 털기 | 등록만 해 두고 30일 넘게 안 간 "곧 잊혀짐" 식당만 모아 [미뤄둔 곳 뽑기]로 뽑는다. |
| S8 | 최후의 1곳 | 토너먼트 모드로 4곳을 받아 하나씩 지워 마지막 1곳을 정하고 방문 처리한다. |
| S9 | 편식 점검 | 추천 화면 상단의 "중식 안 먹은 지 23일째"를 눌러 해당 카테고리에서 뽑는다. |
| S10 | 월말 회고 | `#/visits/stats`에서 이번 달 카테고리 분포, 최다 방문 식당, 추천 수락 비율을 본다. |

## 5. 기능 요구사항

우선순위: **P0** = MVP 필수, **P1** = MVP 포함 권장, **P2** = 이후 개선.

### 5.1 식당 관리

| ID | 기능 | 설명 | 우선순위 |
|----|------|------|----------|
| FR-01 | 식당 등록 | 이름(필수), 카테고리(필수), 상태(필수) 외 선택 항목을 입력해 식당을 등록한다. | P0 |
| FR-02 | 식당 목록 조회 | 등록된 식당을 목록으로 보여준다. 기본 정렬은 최근 등록순이다. | P0 |
| FR-03 | 식당 상세 조회 | 식당의 모든 필드와 최근 방문 이력을 보여준다. | P0 |
| FR-04 | 식당 수정 | 모든 필드를 수정할 수 있다. | P0 |
| FR-05 | 식당 삭제 | 식당을 삭제한다. 삭제 전 확인창을 띄우고, 연결된 방문 기록도 함께 삭제한다. | P0 |
| FR-06 | 즐겨찾기 | 식당에 즐겨찾기 표시를 켜고 끌 수 있다. 목록에서 즐겨찾기만 모아 볼 수 있다. | P1 |
| FR-07 | 태그 | 식당에 자유 태그(예: 혼밥, 국물, 회식)를 여러 개 붙인다. 태그로 필터링한다. | P2 |

### 5.2 식당 정보 필드

| 필드 | 필수 | 설명 / 값 |
|------|------|-----------|
| 이름 | O | 1~100자 |
| 카테고리 | O | 한식 / 중식 / 일식 / 양식 / 분식 / 기타 |
| 상태 | O | `자주 감`(REGULAR) / `가보고 싶음`(WISHLIST). 기본값은 가보고 싶음 |

| 위치/주소 | X | 텍스트 (예: "역삼역 3번 출구 앞"). 지도 연동 없음 |
| 메모 | X | 추천 메뉴, 웨이팅 정보 등 자유 텍스트, 최대 1000자 |
| 즐겨찾기 | X | true/false, 기본 false |
| 태그 | X | 0개 이상 (P2) |
| 출처 상가업소번호 | X | (v0.6) 공공데이터 카탈로그에서 골라 등록했을 때만 채워진다(`place_no`). 사용자가 직접 편집하는 필드가 아니며 폼에는 보이지 않는다(내부 연결용). 수동 입력 식당은 NULL |

#### 5.4.1 가중치 공식 (FR-28)

후보 식당 i의 가중치 `w_i`는 아래 네 인자의 곱이다. 추첨은 `w_i / Σw` 확률로 한다(`random.choices`, 외부 라이브러리 불필요).

```
w = elapsed × wishlist_bonus × favorite_bonus × skip_penalty

elapsed         = 1 + min(days_since_last_visit, 60) / 30   # 방문 이력 있음: 1.0 ~ 3.0 (60일에서 상한)
                  1.0                                         # 방문 이력 없음
wishlist_bonus  = 2.0  (status = WISHLIST 이고 방문 0회)  / 그 외 1.0
favorite_bonus  = 1.2  (is_favorite)                       / 그 외 1.0
skip_penalty    = max(0.5, 1 - 0.1 × consecutive_skips)    # 마지막 방문 이후 연속 넘김 횟수. 5회 이상이면 0.5
```

- `days_since_last_visit` = 오늘 − `MAX(visited_on)` (일 단위). 방문 0회인 식당은 `elapsed`를 1.0으로 두고 대신 WISHLIST 보너스(2.0)를 받는다. 방문 0회인 REGULAR는 보너스 없이 1.0이다.
- 가중치 범위는 최소 0.5(5회 이상 넘김, 방금 방문)에서 최대 3.6(60일 이상 미방문, 즐겨찾기)이며, 모든 가중치가 양수라 후보가 0이 되는 경우는 없다. 최대/최소 비율이 약 7배로 제한되어 한 곳에 쏠리지 않는다.
- 넘긴 횟수 감점을 **반영한다**(결정). 이유: 사용자가 반복해서 넘긴 식당은 이미 선호하지 않는다는 신호이고, 데이터가 이미 있어 비용이 작다. 하한 0.5로 두어 완전 배제는 하지 않는다(완전 제거는 FR-51의 사용자 결정에 맡긴다).
- 상수(60일, 30일, 2.0, 1.2, 0.1, 0.5)는 백엔드 서비스 모듈의 상수로 두고 환경변수로 노출하지 않는다.
- 선택 파라미터: `weighted`(bool, **기본 true**). `false`면 종전의 균등 추첨이다. 모드 선택 UI는 두지 않는다(프론트엔드는 항상 기본값 사용, `curl` 검증과 비교용으로만 존재). 이렇게 하면 API가 하나이고 화면이 단순하다.

**수용 기준**
- 같은 후보 집합에서 `weighted=true`로 충분히 많이(예: 1,000회) 뽑으면 오래 안 간 식당, 미방문 WISHLIST, 즐겨찾기 식당이 균등일 때보다 더 자주 나온다(`curl` 반복으로 수동 확인).
- `exclude_recent_days`로 제외된 식당과 `exclude_id` 식당(후보가 2곳 이상일 때)은 가중치와 무관하게 절대 나오지 않는다.
- 후보가 1곳이면 그 식당이 항상 나온다. 후보가 없으면 종전대로 `404 NO_CANDIDATES`다.
- `weighted=false`는 FR-20의 균등 추첨과 동일하게 동작한다.

### 5.7 넘긴 기록과 목록 정리 제안

| FR-51 | 연속 넘김 제안 | 마지막 방문 이후 연속 5회(상수 `SKIP_SUGGEST_THRESHOLD`) 넘긴 식당은 목록과 상세에 "목록에서 뺄까요?" 제안을 표시한다. 선택지는 [삭제](기존 삭제 확인 모달)와 [그대로 두기](FR-52). | P1 |
| FR-52 | 제안 무시 | [그대로 두기]를 누르면 해당 식당의 `skip_dismissed_at`을 현재 시각으로 저장한다. 이후 새로 5회 넘기기 전까지 제안을 숨긴다(카운터 리셋). | P1 |

설계 결정

- **기록 방식은 명시적 API로 한다.** `exclude_id`로 자동 기록하는 안은 채택하지 않는다. 이유: (1) 추천 API는 상태 변경이 없는 GET이라는 원칙(7.2)을 지킨다. GET에 쓰기 부작용이 생기면 프리페치·새로고침·`curl` 확인에서도 기록이 쌓인다. (2) `exclude_id`는 "직전 결과 제외"일 뿐 "사용자가 넘김"이라는 의도를 담지 않는다(토너먼트나 운명 모드 등 다른 흐름에서도 쓰일 수 있다). 의도를 아는 쪽은 프론트엔드이고, 영속화는 백엔드가 담당하는 것이 계층 책임에 맞다. (3) 구현이 단순하다(INSERT 한 건). 대가로 호출이 1회 늘지만 실패해도 추천 흐름을 막지 않도록 프론트엔드는 실패를 무시한다(토스트 없음).
- 지운 식당(토너먼트)은 **기록하지 않는다**(FR-61 참고). 운명 모드의 마지막 결과는 다시 뽑기가 불가능하므로 기록 대상이 아니다.
- "마지막 방문 이후 연속 넘김 수" `consecutive_skips` = `skipped_at`의 날짜가 마지막 방문일(`MAX(visited_on)`)보다 **엄밀히 큰** 넘김 수(방문 0회면 전체). 같은 날 수락 직전에 넘긴 기록은 세지 않는다. 방문이 새로 생기면 자연히 0으로 돌아간다(별도 리셋 작업 없음).
- 제안 노출 조건: `skip_suggestion = true` ⇔ (`skipped_at`이 `skip_dismissed_at`보다 나중이면서 날짜가 마지막 방문일보다 큰 넘김 수) ≥ 5. `skip_dismissed_at`이 NULL이면 `consecutive_skips ≥ 5`와 같다.
- 가중치의 감점(5.4.1)에는 무시와 무관하게 `consecutive_skips`를 그대로 쓴다.
- 식당 목록·상세·추천 결과 응답에 `consecutive_skips`(int)와 `skip_suggestion`(bool)을 추가한다. 목록은 한 번의 집계 쿼리(LEFT JOIN + GROUP BY)로 계산해 N+1을 피한다.

**수용 기준**
- 다시 뽑기를 누를 때마다 직전 식당의 넘김 레코드가 1건 생긴다. 수락(방문 처리)이나 최초 뽑기에서는 생기지 않는다.
- 존재하지 않는 식당 ID로 기록하면 `404 NOT_FOUND`다.
- 어떤 식당을 방문 처리하면 그 식당의 `consecutive_skips`는 0이 되고 제안이 사라진다.
- 연속 5회 넘긴 식당의 목록 행과 상세 화면에 "목록에서 뺄까요?"가 [삭제]·[그대로 두기]와 함께 보인다. 4회 이하면 보이지 않는다.
- [그대로 두기] 후에는 제안이 사라지고, 이후 5회를 더 넘기면 다시 나타난다. [삭제]는 FR-05와 같이 확인 모달을 거친다.
- 식당을 삭제하면 넘김 기록도 함께 삭제된다(FK CASCADE).

**수용 기준**
- `created_at`이 31일 전이고 방문 0회인 WISHLIST는 `is_expiring=true`, 29일 전이면 `false`다. REGULAR이거나 방문이 있으면 항상 `false`다.
- `stale_wishlist=true` 응답은 항상 `is_expiring=true`인 식당뿐이다.

| FR-60 | 운명 모드 | 프론트엔드 전용. 켜면 한 번의 뽑기 흐름에서 결과를 최대 3번까지만 볼 수 있고, 3번째 결과는 [여기로 갈래요]만 가능하다([다시 뽑기] 비활성). | P1 |
| FR-61 | 토너먼트(거부권) 모드 | 조건에 맞는 서로 다른 후보 4곳(부족하면 가능한 수)을 받아 하나씩 지워 최후 1곳을 남기고, 수락하면 방문 기록(`source=RECOMMENDATION`)을 만든다. | P1 |

**FR-60 운명 모드**
- 백엔드·DB 변경 없음. 설정은 `localStorage` 키 `dinner.fateMode`(`"1"`/없음)에 저장하며 추천 화면의 토글로 켜고 끈다. 기존 조건 저장(FR-33)과 별개 키다.
- 한 번의 흐름 = [추천받기] 또는 [미뤄둔 곳 뽑기]로 시작해 수락하거나 조건을 바꿔 새로 시작하기 전까지. 시작 시 카운터는 1이고 [다시 뽑기]마다 1 증가한다. 카운터는 메모리에만 두며 새로고침하면 초기화된다.
- 3번째 결과에서는 [다시 뽑기]를 `disabled`로 두고 "운명입니다" 문구를 표시한다. 3번째 결과는 넘기지 못하므로 넘긴 기록은 최대 2건/흐름이다.
- "다시 뽑기 최대 3회"를 "결과 최대 3번(최초 1회 + 다시 뽑기 2회)"으로 해석했다(14장 확인 사항).
- **수용 기준**: 토글을 켠 상태로 새로고침해도 유지된다. 켜면 3번째 결과에서 [다시 뽑기]가 비활성이고 [여기로 갈래요]는 동작한다. 끄면 제한이 사라진다. 조건을 바꿔 [추천받기]를 다시 누르면 카운터가 1로 돌아간다.

**FR-61 토너먼트 모드**
- API: 별도 엔드포인트 `GET /api/v1/recommendations/candidates`를 둔다(7.2.1). `GET /random`에 `count`를 붙이지 않는 이유: 응답 형태(객체 1개 vs 배열)가 달라 하나의 엔드포인트에 두면 계약이 모호해진다. 필터·가중치 로직은 서비스 계층에서 공유한다.
- 흐름: 모드 토글 ON, [추천받기] → 후보 카드 N장(2~4장, 1장이면 곧바로 최종 결과)이 나란히 표시 → 카드의 [지우기]로 하나씩 제거(되돌리기 없음) → 1장 남으면 최종 결과 카드와 [여기로 갈래요] → `POST /visits` (`source=RECOMMENDATION`).
- 후보가 정확히 4곳 미만이면 있는 만큼 사용한다. 0곳이면 `404 NO_CANDIDATES`로 FR-25와 같이 처리한다. 후보는 가중치 비복원 추첨으로 서로 다르게 뽑는다(`exclude_id` 파라미터는 지원하지 않음).
- **지운 식당은 넘긴 기록에 포함하지 않는다**(결정). 이유: 토너먼트에서는 한 세션에 3곳이 한꺼번에 지워져 "넘김 5회 연속" 제안과 가중치 감점이 과하게 쌓이고, 지움은 "싫다"가 아니라 "이번엔 이곳이 더 낫다"는 상대 비교이기 때문이다. 이에 따라 월간 통계의 "넘김 횟수"도 [다시 뽑기] 기준이다.
- **수용 기준**: 4곳 이상 조건일 때 서로 다른 4곳이 표시되고 3번 지우면 1곳이 남는다. 후보가 3곳이면 3장, 1곳이면 지우기 없이 최종 결과가 된다. 수락하면 방문 기록이 `source=RECOMMENDATION`으로 1건만 생긴다. 지우는 동안 `recommendation_skips`에는 아무 것도 쌓이지 않는다.

**FR-70 카테고리 공백 알림**
- 대상 카테고리: 등록된 식당이 1곳 이상인 카테고리 중 `ETC`(기타)를 제외한 것. 식당이 없는 카테고리는 알림 대상이 아니다(뽑을 곳이 없으므로).
- 카테고리의 마지막 방문일 = 그 카테고리 식당들의 `MAX(visited_on)`. `days_since` = 오늘 − 마지막 방문일.
- 선정 규칙: **방문 이력이 아예 없는 카테고리**(식당은 있음)가 있으면 우선(여럿이면 카테고리 enum 순서로 첫 번째), 없으면 `days_since`가 가장 큰 카테고리. 선정된 카테고리가 방문 이력 있음이면 `days_since ≥ 7`(상수 `CATEGORY_GAP_MIN_DAYS`)일 때만 알림을 낸다.
- 표시 문구: 방문 이력 있음 "중식 안 먹은 지 23일째", 없음 "일식은 아직 가본 기록이 없어요". 전체 방문 기록이 0건이면 알림을 표시하지 않는다(신규 사용자에게 모든 카테고리가 "없음"이 되는 노이즈 방지).
- 클릭 동작: 카테고리 칩을 해당 카테고리 하나만 선택된 상태로 바꾸고(기존 가격대·상태 등 다른 조건은 유지), 바로 뽑는다. 조건이 바뀌므로 FR-33에 따라 저장된다.
- API: `GET /api/v1/stats/category-gap` (7.1). 알림 후보가 없으면 `gap: null`.
- **수용 기준**: 한식은 어제, 중식은 23일 전 방문, 양식은 식당만 있고 방문 없음이면 양식이 "아직 가본 기록이 없어요"로 표시된다. 양식 식당이 없다면 중식이 "안 먹은 지 23일째"로 표시된다. 모든 카테고리가 7일 이내 방문이면 알림이 없다. 클릭하면 해당 카테고리만으로 후보 1곳이 표시되거나(후보가 없으면 NO_CANDIDATES 안내) 한다.

**FR-71 월간 식생활 회고**
- 기간: 선택한 달의 1일~말일(서버 로컬 시간대 기준). 기본은 이번 달이며 [이전 달]/[다음 달]로 이동한다(미래 달은 비활성).
- 지표 정의
  - 총 방문 수: 해당 월 `visits` 건수(같은 날 중복 포함).
  - 카테고리 분포: 방문 건수를 카테고리별로 집계(건수·비율). 방문 0건인 카테고리는 응답에서 생략하거나 0으로 둔다(화면은 0건 막대를 그리지 않는다).
  - 최다 방문 식당: 방문 건수 상위 3곳(동률이면 최근 방문일이 늦은 쪽, 그다음 이름순). 화면은 1위를 강조한다. 방문이 없으면 빈 배열.
  - 최장 연속 동일 카테고리: 월 내 방문을 (`visited_on`, `id`) 순으로 나열해 같은 카테고리가 연달아 이어진 최대 길이와 그 카테고리·기간. 길이가 같으면 먼저 발생한 구간. 월 경계를 넘는 연속은 합치지 않는다. 방문이 없으면 `null`.
  - 추천 수락 비율: `source=RECOMMENDATION` 방문 수 / 총 방문 수(총 0이면 `null`, 화면은 "-").
  - 넘김 횟수: 해당 월 `recommendation_skips` 건수(다시 뽑기 기준, 토너먼트 제외).
- 막대 표시: `div` 폭을 `width: N%`로 지정하는 CSS 막대. 값은 숫자로도 함께 표기해 색에만 의존하지 않는다. 사용자 입력(식당명)은 `textContent`로 출력한다.
- 데이터 없음: 방문이 0건인 달은 "이 달의 기록이 없어요" 빈 상태를 보여준다(넘김 횟수는 그대로 표시).
- **수용 기준**: 샘플 방문으로 각 지표가 수작업 계산과 일치한다. 다른 달로 이동하면 해당 달 값으로 바뀐다. 방문이 0건이어도 오류 없이 빈 상태를 표시한다. 번들에 차트 라이브러리가 추가되지 않는다(`package.json` 의존성 변동 없음).

#### 5.11.1 설계 결정

- **CSV를 `restaurants`에 직접 넣지 않는다**(결정). 이유: (1) `restaurants`는 사용자가 고른 "내 목록"이며, 시도 단위만 해도 음식점이 수만~수십만 건이라 직접 넣으면 목록·무작위 추천이 사실상 동네 전체 식당에서 뽑게 되어 추천의 의미가 사라진다. (2) 상태(자주 감/가보고 싶음)·가격대·메모·즐겨찾기 같은 개인 정보는 임포트 데이터에 없다. (3) 카탈로그를 재임포트·초기화해도 개인 데이터가 영향받지 않아야 한다. 따라서 카탈로그는 별도 테이블 `places`에 두고, 사용자가 고른 한 건만 복사해서 `restaurants` 행을 만든다.
- **`restaurants.place_no`(상가업소번호, nullable)를 추가한다**(결정). `places.id`가 아니라 원본의 안정 식별자인 상가업소번호를 문자열로 저장한다. 이유: `places`를 비우고 다시 임포트해도 연결이 유지되고, 외래키 없이도 "이미 등록됨" 판정(`EXISTS`)이 가능하다. **FK는 걸지 않는다**: 카탈로그 갱신·삭제가 개인 목록에 영향을 주면 안 되며, 복사된 이름·주소는 `restaurants`가 자체 보관하므로 `places`가 없어도 식당은 완전하다. 용도는 (a) 등록 여부 표시, (b) 향후 갱신 추적이다. 동일 `place_no`의 중복 등록은 허용한다(UNIQUE 아님).
- **좌표(경도·위도)는 저장만 한다.** 거리 계산·정렬·지도 표시는 범위 밖이며 13장 로드맵(지도 연동)에서 다룬다. `restaurants`에는 좌표를 복사하지 않는다.
- 임포트는 **수동·일회성 운영 작업**이다. CSV는 사용자가 공공데이터포털에서 직접 내려받는다. 원본 CSV는 저장소에 커밋하지 않으며(`.gitignore`에 `backend/data/` 등록, 권장 보관 경로) 파일 크기·라이선스 관리를 사용자에게 맡긴다.
- 검색은 외부 호출 없이 내부 DB만 조회한다. 프론트엔드는 `/api/v1/places`만 호출하며 CSV나 DB에 접근하지 않는다(3티어 원칙 유지).

```
uv run python -m app.scripts.import_places <csv경로> [--sido 서울특별시] [--sigungu 강남구] [--dong 역삼1동] [--dry-run]
```

- 경로의 파일 하나를 처리한다. 시도별 CSV가 여러 개면 파일마다 실행한다.
- **인코딩**: 먼저 `utf-8-sig`로 시도하고 실패하면 `cp949`로 읽는다(공공데이터 CSV는 CP949인 경우가 많음). 사용한 인코딩을 출력한다.
- **컬럼 매칭**: 헤더의 한글 컬럼명으로 찾으며 순서에 의존하지 않는다. 필수 컬럼: 상가업소번호, 상호명, 상권업종대분류명, 상권업종중분류명, 시도명, 시군구명. 선택 컬럼: 지점명, 상권업종소분류명, 행정동명, 도로명주소, 지번주소, 경도, 위도. 개편 전후로 컬럼명·일부 컬럼 유무가 다를 수 있어, 필수 컬럼이 없으면 누락된 컬럼 이름을 보여주고 종료 코드 1로 끝낸다. 선택 컬럼이 없으면 NULL로 둔다. 행정동명과 법정동명이 모두 있으면 행정동명을 쓴다.
- **필터**: 상권업종대분류명이 '음식'인 행만. `--sido`, `--sigungu`, `--dong`은 각각 해당 컬럼과 **완전 일치 또는 접두 일치**(예: `--sigungu 강남`)로 걸러내며, 여러 번 지정하면 AND다. 지정하지 않으면 해당 축은 제한 없음이다.
- **적재**: 5.11.2 매핑 후 제외 대상은 건너뛴다. 상가업소번호 기준 `INSERT ... ON DUPLICATE KEY UPDATE`(배치 1,000행 단위)로 멱등하게 적재하고 `imported_at`을 갱신한다. 상호명이 비거나 상가업소번호가 없는 행은 건너뛴다.
- **출력 요약**: 읽은 행 수, 음식 업종 아닌 행 수, 지역 필터로 제외된 수, 매핑 제외(술집·카페) 수, ETC로 적재된 수, 신규 추가/갱신 수, 소요 시간. `--dry-run`이면 DB에 쓰지 않고 요약만 출력한다.
- DB 접속은 백엔드 `.env`를 그대로 쓴다. 대용량(수십만 행)에서도 메모리에 전부 올리지 않도록 스트리밍으로 읽는다.
- **수용 기준**: 같은 파일을 두 번 실행해도 `places` 행 수가 늘지 않는다. 지역 필터를 주면 해당 지역 행만 들어간다. UTF-8과 CP949 파일을 모두 읽는다. 주점·카페 업종은 적재되지 않는다.

#### 5.11.4 검색과 폼 자동 채움 (FR-83~85)

- **검색 방식**: `q`를 공백으로 나눈 각 토큰이 `name`, `branch_name`, `sigungu`, `dong`, `road_address` 중 하나에 부분 일치해야 한다(토큰끼리 AND). 예: "역삼 김밥", "강남구 칼국수". 부분 일치 `LIKE '%토큰%'`을 쓰므로 MariaDB의 인덱스는 이름 접두 검색에만 도움이 되고, 임포트를 지역 단위로 제한하는 것을 전제로 규모(수만 건)를 관리한다. MariaDB에는 한국어 ngram FULLTEXT가 없으므로 FULLTEXT는 쓰지 않는다.
- `q`는 2자 이상이다(1자는 `422`). `limit` 기본 20, 최대 50. 정렬은 상호명이 `q` 첫 토큰으로 시작하는 행 우선, 그다음 상호명 순.
- **폼 채움 규칙**: 이름 = 상호명 + (지점명이 있으면 공백 + 지점명, 100자 초과 시 잘라냄), 위치 = 도로명주소(없으면 지번주소, 255자 초과 시 잘라냄), 카테고리 = `places.category`. 상태·가격대·메모·즐겨찾기는 건드리지 않는다(기본값 가보고 싶음 유지). 숨은 값으로 `place_no`를 들고 있다가 저장 시 `POST /restaurants`에 함께 보낸다. 사용자가 폼의 이름·위치·카테고리를 수정해도 `place_no` 연결은 유지한다.
- 검색창은 입력 후 300ms 디바운스로 호출하고, 결과 목록은 `textContent`로 렌더링한다(상호명·주소는 외부 데이터이므로 `innerHTML` 금지). 결과 항목에는 상호명·지점명, 카테고리 라벨, 주소, "등록됨" 배지(FR-85)를 보인다.
- 카탈로그가 비어 있으면(`places` 0건) 검색 영역에 "공공데이터가 아직 없어요. 임포트 후 사용할 수 있어요" 안내를 표시하고 수동 입력은 정상 동작한다. 수정 화면(`/restaurants/:id/edit`)에는 검색 영역을 두지 않는다(등록 전용).
- **수용 기준**: "공공데이터에서 찾기"에서 결과를 선택하면 이름·위치·카테고리가 채워지고 값을 고쳐 저장할 수 있다. 저장된 식당은 `place_no`를 가지며 같은 장소가 다음 검색에서 "등록됨"으로 보인다. 검색 없이 수동으로 입력해 저장한 식당의 `place_no`는 NULL이다. `places`가 비어 있어도 오류 없이 수동 등록이 된다. 결과는 `limit`을 넘지 않는다.

#### 5.11.5 출처 표기 (FR-86)

- 이용허락: 공공데이터포털 데이터셋 페이지(data.go.kr/data/15083033/fileData.do) 표기는 "**이용허락범위 제한 없음**"이며 공공누리 유형 표기는 없다(2026-10-14 확인, 20260630 파일 기준). 의무 사항은 아니지만 출처를 표기한다.
- 표시 위치: (1) 식당 추가 화면의 "공공데이터에서 찾기" 영역 하단, (2) 앱 공통 푸터(모든 화면 하단, 작은 글씨). 문구: "식당 검색 데이터 출처: 소상공인시장진흥공단 「상가(상권)정보」 2026.06 기준, 공공데이터포털(data.go.kr) · 이용허락범위 제한 없음". 기준월은 재임포트 시 갱신한다. 푸터 문구는 카탈로그 데이터가 1건 이상 있을 때만 표시해도 된다.
- 문구는 프론트엔드 상수로 두고, 기준월·이용허락 변경 시 수정할 수 있게 한 곳(예: `frontend/src/` 내 단일 상수)에 모은다.
- 원본 데이터는 카테고리 매핑 외에는 변형하지 않고 검색 보조용으로만 사용하며, 앱은 원본 CSV나 전체 데이터를 외부에 재배포하지 않는다.

| category | ENUM('KOREAN','CHINESE','JAPANESE','WESTERN','SNACK','ETC') | NOT NULL | 카테고리 |

### 6.6 관계

```
restaurants 1 ──< N visits
restaurants 1 ──< N recommendation_skips   (v0.5)
restaurants N ──< restaurant_tags >── N tags   (P2)
restaurants N ··· 0..1 places   (v0.6, restaurants.place_no = places.place_no, 논리적 참조만, FK 없음)
```

"마지막 방문일", "연속 넘김 수", "곧 잊혀짐 여부", 카테고리별 마지막 방문일, 월간 통계, 장소 "등록됨" 여부(`already_registered`)는 모두 별도 컬럼으로 저장하지 않고 `visits`·`recommendation_skips`에서 조회 시 계산한다(정합성 우선, 데이터 규모가 작음).

## 7. API 명세 (초안)

- Base path: `/api/v1`, 형식: JSON, 문자셋 UTF-8
- 문서: FastAPI 자동 문서(`/docs`)를 개발 환경에서 제공한다.

- 입력 검증은 Pydantic 스키마로 수행하며 실패 시 `422`를 반환한다.

### 7.2 추천 API 상세

`GET /api/v1/recommendations/random`

| 파라미터 | 타입 | 기본값 | 설명 |
|----------|------|--------|------|
| category | string, 복수 가능 | 전체 | `KOREAN`, `CHINESE` 등. 반복 지정 시 OR (`?category=KOREAN&category=JAPANESE`) |
| price_level | int, 복수 가능 | 전체 | 1~4. 반복 지정 시 OR |
| status | string | 전체 | `REGULAR` 또는 `WISHLIST` |
| is_favorite | bool | 미적용 | true면 즐겨찾기만 |
| exclude_recent_days | int | 7 | 0~90. 최근 N일 내 방문한 식당 제외 |
| exclude_id | int | 없음 | 직전 추천 결과 제외 (다시 뽑기용) |
| weighted | bool | true | (v0.5) true면 5.4.1 공식의 가중 추첨, false면 균등 추첨 |
| stale_wishlist | bool | false | (v0.5) true면 `is_expiring`(곧 잊혀짐) 식당만 후보로 한다(FR-56) |

응답 200 예시:

```json
{
  "restaurant": {
    "id": 12,
    "name": "을지로 칼국수",
    "category": "KOREAN",
    "status": "REGULAR",
    "price_level": 1,
    "location": "을지로3가역 근처",
    "memo": "점심 웨이팅 15분",
    "is_favorite": true,
    "last_visited_on": "2026-09-30",
    "is_expiring": false,
    "consecutive_skips": 0,
    "skip_suggestion": false
  },
  "candidate_count": 8
}
```

- 후보가 없으면 `404`와 `NO_CANDIDATES` 코드를 반환한다. 프론트엔드는 이를 안내 메시지로 표시한다.
- 추천 결과는 서버에 저장하지 않는다(추천은 상태 변경이 없는 GET). 수락 시점에 `POST /visits`로 기록한다.
- 선택 로직은 백엔드 서비스 계층에서 구현한다(필터링 후 `weighted=true`면 5.4.1 공식의 가중 추첨, `false`면 `random.choice`).
- 넘김은 서버가 추천 시점에 기록하지 않는다. 프론트엔드가 [다시 뽑기] 시 `POST /recommendations/skips`로 알린다(5.7의 결정).

### 7.2.1 후보 목록 API (토너먼트)

`GET /api/v1/recommendations/candidates` — 필터 파라미터(`category`, `price_level`, `status`, `is_favorite`, `exclude_recent_days`, `stale_wishlist`, `weighted`)는 `random`과 같다. 추가로 `count`(int, 기본 4, 1~8)를 받는다.

```json
{
  "restaurants": [ { "id": 12, "name": "...", "...": "random의 restaurant와 같은 필드" }, { "id": 7 } ],
  "candidate_count": 8
}
```

- `restaurants`는 서로 다른 식당이며 길이는 `min(count, 후보 수)`다. 후보가 없으면 `404 NO_CANDIDATES`.
- 기록은 남기지 않는 GET이다. 수락은 `POST /visits`(`source=RECOMMENDATION`)로 한다.

### 7.2.2 넘김·제안 무시 API

- `POST /api/v1/recommendations/skips` body `{"restaurant_id": 12}` → `201 {"id": 1, "restaurant_id": 12, "skipped_at": "2026-10-14T12:30:00"}`. 없는 식당이면 `404 NOT_FOUND`, 형식 오류면 `422`.
- `POST /api/v1/restaurants/{id}/skip-suggestion/dismiss` → `204`. `skip_dismissed_at`을 현재 시각으로 설정한다. 없는 식당이면 `404`. 제안이 없는 식당에 호출해도 오류 없이 시각만 갱신한다(멱등).

### 7.2.3 통계 API

`GET /api/v1/stats/category-gap`

```json
{
  "gap": { "category": "CHINESE", "last_visited_on": "2026-09-21", "days_since": 23, "restaurant_count": 3 },
  "categories": [
    { "category": "KOREAN", "restaurant_count": 9, "last_visited_on": "2026-10-13", "days_since": 1 },
    { "category": "WESTERN", "restaurant_count": 2, "last_visited_on": null, "days_since": null }
  ]
}
```

- `categories`는 식당이 1곳 이상인 카테고리만 포함한다(`ETC` 포함, 표시 대상 선정에서만 제외). `gap`은 FR-70의 선정 규칙 결과이며 알림 대상이 없으면 `null`. `gap.days_since`가 `null`이면 방문 기록 없음.

`GET /api/v1/stats/monthly?month=2026-10` (잘못된 형식이나 미래 달은 `422`)

```json
{
  "month": "2026-10",
  "total_visits": 14,
  "category_distribution": [ { "category": "KOREAN", "count": 8, "ratio": 0.571 } ],
  "top_restaurants": [ { "restaurant_id": 12, "name": "을지로 칼국수", "count": 4 } ],
  "longest_category_streak": { "category": "KOREAN", "length": 3, "from": "2026-10-05", "to": "2026-10-07" },
  "recommendation": { "accepted_count": 9, "accept_ratio": 0.643 },
  "skip_count": 12
}
```

- `ratio`, `accept_ratio`는 0~1 소수. 방문이 0건이면 `category_distribution`·`top_restaurants`는 빈 배열, `longest_category_streak`·`accept_ratio`는 `null`.
- 삭제된 식당의 방문은 FK CASCADE로 이미 사라지므로 통계에도 포함되지 않는다(식당 삭제 시 과거 통계가 변할 수 있음을 허용).

### 7.2.4 장소 카탈로그 API (v0.6)

`GET /api/v1/places?q=역삼 김밥&limit=20`

| 파라미터 | 타입 | 기본값 | 설명 |
|----------|------|--------|------|
| q | string | 필수 | 2~50자. 공백으로 나눈 토큰 모두가 상호명·지점명·시군구·행정동·도로명주소 중 하나에 부분 일치(AND). 1자 이하이거나 없으면 `422` |
| category | string, 복수 가능 | 전체 | 앱 카테고리 ENUM, 반복 지정 시 OR |
| limit | int | 20 | 1~50 |

```json
{
  "items": [
    {
      "id": 1021,
      "place_no": "MA010120220800001234",
      "name": "김밥천국",
      "branch_name": "역삼점",
      "category": "SNACK",
      "industry_mid": "분식",
      "industry_small": "김밥/만두/분식",
      "location": "서울특별시 강남구 테헤란로 123",
      "sido": "서울특별시",
      "sigungu": "강남구",
      "dong": "역삼1동",
      "already_registered": false
    }
  ],
  "count": 1,
  "limit": 20
}
```

- `location`은 도로명주소(없으면 지번주소)이며 폼의 위치 필드에 쓰인다. 좌표(`lat`, `lon`)는 응답에 포함하지 않는다(저장만).
- `already_registered`는 `EXISTS (SELECT 1 FROM restaurants WHERE place_no = places.place_no)`로 계산한다(N+1 없이 한 쿼리).
- 결과가 없으면 `200`과 빈 `items`다(404 아님). 읽기 전용 GET이며 쓰기 부작용이 없다.
- `POST /restaurants`와 `PUT /restaurants/{id}`는 `place_no`(선택, 최대 30자)를 받아 저장한다. 존재하지 않는 `place_no`도 오류로 처리하지 않는다(FK 없음, 카탈로그 재임포트와 독립). 응답의 식당 객체에도 `place_no`를 포함한다. `PUT`에서 `place_no`를 생략하면 기존 값을 유지한다.

### 7.2.5 식당 통합 검색 API (v0.8)

내 식당과 공공데이터 식당을 한 목록으로 반환하는 읽기 전용 GET 두 개(`/api/v1/restaurants/search`, `/api/v1/restaurants/search/random`)다. 라우트는 `/restaurants/{id}`보다 먼저 선언한다. 기존 `GET /restaurants`(7.1), `GET /places?q=`(7.2.4), `GET /places/regions`는 그대로 유지한다. v0.7의 `GET /places/browse`·`/places/random`은 이 API로 대체되어 삭제했다. 스키마 변경이 없어 마이그레이션은 추가하지 않는다.

**공통 필터**: `q`(최대 100자), `category`(복수, OR), `sigungu`, `dong`, `price_level`(복수), `status`, `is_favorite`. 공공데이터 포함 규칙은 FR-92(키워드·카테고리·지역 중 하나 이상, 그리고 `status`/`price_level`/`is_favorite` 없음)이며, 내 식당 지역 판정은 5.12의 근사 규칙이다. 공공데이터는 `place_no`가 `restaurants`에 있는 것을 `NOT EXISTS`로 제외한다.

**`GET /restaurants/search?...&sort=created_desc&offset=0&limit=20`**: `sort`는 내 식당 정렬(7.1과 동일), `limit` 1~50(기본 20). 정렬은 내 식당(`sort`) 먼저, 이어서 공공데이터(상호명, id). `offset`이 `mine_total`을 넘는 지점부터 공공데이터를 `offset - mine_total`로 잘라 채운다.

```json
{
  "items": [
    { "kind": "mine", "id": 3, "name": "…", "category": "KOREAN", "status": "WISHLIST", "place_no": null, "…": "RestaurantOut 필드" },
    { "kind": "place", "id": 70119, "place_no": "MA01…", "name": "…", "branch_name": null, "category": "KOREAN",
      "industry_mid": "한식", "industry_small": "…", "location": "…", "sido": "서울특별시", "sigungu": "강남구",
      "dong": "역삼1동", "already_registered": false }
  ],
  "total": 98, "mine_total": 2, "place_total": 96, "limit": 20, "offset": 0
}
```

`items`는 `kind`로 구분하는 판별 유니온이다(`mine`은 `RestaurantOut`, `place`는 `PlaceOut`(7.2.4) 필드). 통합 목록의 공공데이터는 항상 `already_registered=false`다.

**`GET /restaurants/search/random?...&mine_only=false`**: 같은 필터로 합쳐진 후보(`mine_total + place_total`)에서 균일 무작위 1건을 위 `items` 요소 형식으로 반환한다. 인덱스를 하나 뽑아 해당 쪽에서 `offset` 조회하며 `ORDER BY RAND()`는 쓰지 않는다. `mine_only=true`면 공공데이터를 후보에서 뺀다. 후보가 없으면 `404 NOT_FOUND`(`{"error":{...}}`).

## 9. 비기능 요구사항

| 구분 | 요구사항 |
|------|----------|
| 3티어 분리 | 프론트엔드, 백엔드, DB는 각각 별도 디렉터리(`frontend/`, `backend/`, `db/`)와 별도 프로세스로 구성한다. 계층 간 통신은 네트워크 프로토콜(HTTP, MariaDB 프로토콜)만 사용하고 파일·코드를 직접 공유하지 않는다. |
| 데이터 접근 경로 | 프론트엔드는 백엔드 REST API로만 데이터를 요청한다. DB 직접 접근은 금지한다. |
| 환경변수 | 주소·포트·접속 정보는 `.env`로 주입하고 하드코딩하지 않는다. `.env`는 커밋하지 않고 `.env.example`만 관리한다. |
| DB 접속정보 | 호스트, 포트, 사용자, 비밀번호, DB명은 백엔드 `.env`에만 둔다. 프론트엔드 번들에는 API 경로(`VITE_API_BASE_URL=/api/v1`)만 포함한다. 브라우저는 프론트엔드 서버의 `/api`로 요청하고, 프론트엔드 서버(Vite dev/preview 프록시)가 `API_PROXY_TARGET`의 백엔드로 전달한다. |
| CORS | 백엔드는 허용 Origin 목록을 `CORS_ALLOW_ORIGINS` 환경변수로 받아 해당 Origin만 허용한다. 와일드카드(`*`)는 사용하지 않는다. |
| 입력 검증 | 모든 입력은 Pydantic으로 타입·길이·범위·enum을 검증한다. DB 접근은 ORM(SQLAlchemy) 또는 바인딩 파라미터만 사용해 SQL 인젝션을 막는다. |
| 출력 안전 | 프론트엔드는 사용자 입력을 `textContent`/`createElement`로 렌더링하고, 사용자 데이터를 `innerHTML`에 넣지 않는다. |
| 공공데이터 출처·보관 | (v0.6) 원본 CSV와 임포트 산출물(`backend/data/` 등)은 저장소에 커밋하지 않고 `.gitignore`에 등록한다. 화면에 데이터 출처 문구를 표시한다(5.11.5). 카탈로그 검색 API는 결과 상한(최대 50건)과 최소 검색어 길이(2자)를 강제한다. 상호명·주소는 외부 데이터이므로 `textContent`로만 출력한다. |
| 응답시간 | 개발 서버 기준 목록·추천 API p95 300ms 이하, 헬스체크 50ms 이하. 식당 1,000건, 방문 10,000건 규모까지 보장한다. (v0.6) `GET /places`는 `places` 5만 건 규모(지역 필터 임포트 기준)에서 p95 300ms 이하를 목표로 한다. |
| 기본 보안 | DB 계정은 해당 DB 한정 최소 권한으로 만든다. 오류 응답에 스택트레이스·SQL을 노출하지 않는다. 로그에 비밀번호를 남기지 않는다. 의존성은 버전을 고정한다(백엔드는 `uv.lock`, 프론트엔드는 `package-lock.json` 커밋). |
| 신뢰성 | 백엔드 시작 시 DB 연결을 확인하고, 연결 실패는 `/health`에서 비정상으로 보고한다. DB 덤프를 주기적으로 백업한다(수동 스크립트). |
| 접근성 / 호환성 | 최신 Chrome, Safari, Edge와 모바일 브라우저를 지원한다. 키보드 조작과 `prefers-reduced-motion`을 고려한다. |
| 검증 | 단위 테스트는 작성하지 않는다(사용자 결정). 빌드 성공, 서버 기동, `curl`을 이용한 API 수동 확인, 브라우저 화면 수동 확인으로 검증한다. |

### 10.4 향후 분리 방안
- **프론트엔드 분리**: 정적 빌드 결과물을 별도 웹서버 또는 CDN에 배포한다. 웹서버(Nginx 등)가 `/api`를 백엔드로 프록시하거나, `VITE_API_BASE_URL`을 백엔드 절대 주소로 바꾸고 백엔드 `CORS_ALLOW_ORIGINS`에 프론트엔드 Origin을 추가한다.
- **백엔드 분리**: 별도 서버에 컨테이너 또는 systemd 서비스로 배포한다. `DB_HOST`만 DB 서버 주소로 바꾼다. 역방향 프록시(Nginx)에서 `/api` 경로를 위임할 수 있다.
- **DB 분리**: 별도 서버 또는 매니지드 DB로 이전한다. 백엔드의 방화벽 허용 IP만 열고 TLS 접속을 적용한다. 스키마는 `db/` 마이그레이션으로 재현한다.
- 위 분리 모두 코드 변경 없이 환경변수와 배포 설정만으로 가능해야 한다.

### 10.5 실행 방식 (직접 실행, uv)

컨테이너나 systemd를 쓰지 않고, 각 계층 프로세스를 개발 서버에서 직접 실행한다. 백엔드의 Python 버전, 가상환경, 의존성은 **uv**로 관리한다. `pip`와 `requirements.txt`는 쓰지 않는다.

| 계층 | 준비 | 실행 |
|------|------|------|
| 데이터 | OS 패키지로 MariaDB 설치, `db/schema.sql`·`db/seed.sql` 적용 | OS 서비스로 기동 (`127.0.0.1:3306`) |
| 애플리케이션 | `cd backend && uv sync` | `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` (개발 시 `--reload`) |
| 프레젠테이션 | `cd frontend && npm install` | 개발: `npm run dev` (:5173) / 빌드 확인: `npm run build && npm run preview` |

- (v0.6) 카탈로그 임포트(선택, 최초 1회 및 갱신 시): 공공데이터포털에서 받은 CSV를 `backend/data/`에 두고 `cd backend && uv run python -m app.scripts.import_places data/<파일>.csv --sido <시도> [--sigungu <시군구>] [--dong <행정동>]`. 5.11.3 참고. 서비스 기동 전후 어느 때나 실행할 수 있다.
- 백엔드 의존성 추가는 `uv add <패키지>`, 개발용 도구는 `uv add --dev <패키지>`로 한다.
- `backend/pyproject.toml`, `backend/uv.lock`, `backend/.python-version`을 커밋한다. `.venv/`는 커밋하지 않는다.
- 도구 실행도 `uv run`을 거친다.
- 실행 방법은 `README.md`에 계층별 명령으로 정리한다.
