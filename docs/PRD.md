# PRD: 오늘 뭐 먹지?

## 1. 개요

| 항목 | 내용 |
|------|------|
| 제품명 | 오늘 뭐 먹지? |
| 한 줄 소개 | 자주 가는 식당과 가보고 싶은 식당을 저장해 두고, 고민될 때 조건에 맞는 식당을 무작위로 추천받는 웹앱 |
| 문서 버전 | v0.4 |
| 작성일 | 2026-10-14 |
| 상태 | 초안 (v0.2: 배포 방식 직접 실행, Python 패키지 관리 uv 확정 / v0.3: 프론트엔드 React → Vanilla JS + Vite, 단일 사용자·내부망 확정 / v0.4: 단위 테스트 제외) |
| 기술 스택 | Vanilla JS + Vite (프레젠테이션, UI 프레임워크 미사용) / FastAPI (애플리케이션) / MariaDB (데이터) |
| 실행 방식 | 직접 실행 (컨테이너·systemd 미사용), 백엔드 Python 환경은 uv로 관리 |

본 문서는 기획 초안을 바탕으로 MVP 범위의 요구사항, 데이터 모델, API, 화면, 아키텍처, 일정을 정의한다. 구현은 `CLAUDE.md`의 3티어 분리 원칙을 따른다.

## 2. 배경 및 해결하려는 문제

기획 초안에는 해결할 문제가 비어 있었으므로, 아래 4가지를 구체적인 문제로 정의한다.

| # | 문제 | 상황 예시 | 서비스의 해법 |
|---|------|-----------|---------------|
| P1 | 결정 피로 | 점심·저녁마다 "아무거나"를 반복하며 10분 이상 고민한다. | 조건을 걸고 버튼 한 번으로 후보를 하나 뽑아준다. |
| P2 | 가고 싶던 곳을 잊어버림 | 지나가다 본 식당, 지인이 추천한 식당을 정작 고를 때는 기억하지 못한다. | "가보고 싶음" 상태로 저장하고 추천 후보에 포함한다. |
| P3 | 팀 점심 합의의 어려움 | 여러 명이 의견을 내다 보면 결론이 나지 않거나 특정인이 늘 정하게 된다. | (향후) 공유 목록에서 무작위로 뽑아 합의 비용을 줄인다. MVP는 개인용이다. |
| P4 | 같은 곳만 반복 | 익숙한 몇 곳만 가고, 최근에 갔던 곳이 또 나온다. | 최근 N일 내 방문한 곳을 제외하고, 방문 기록으로 반복 패턴을 확인한다. |

## 3. 목표와 비목표

### 3.1 목표 (MVP)
- G1. 식당을 등록·수정·삭제·조회할 수 있다.
- G2. 카테고리, 가격대, 상태, 최근 방문 제외 조건으로 무작위 추천을 받을 수 있다.
- G3. 추천 결과를 수락하면 방문 기록이 남고, 이후 추천에 반영된다.
- G4. 프론트엔드, 백엔드, DB 세 계층이 역할별로 분리되어 있고 향후 별도 서버로 이전할 수 있다.

### 3.2 비목표 (MVP에서 하지 않음)
- 로그인·회원가입·권한 관리
- 팀 공유방, 투표, 다중 사용자 데이터 분리
- 지도·위치 기반 추천, 외부 맛집 API 연동
- 리뷰·평점의 소셜 기능, 사진 업로드
- 모바일 네이티브 앱 (반응형 웹으로만 대응)

### 3.3 전제 (Assumption)
- **MVP는 개인 사용, 단일 사용자를 기준으로 시작한다.** 사용자 식별 없이 하나의 데이터 집합만 존재한다.
- 팀 공유와 로그인은 비목표이며 13장의 로드맵으로 둔다. 다만 확장 시 부담을 줄이기 위해 데이터 모델에 `owner_id` 등을 지금 넣지는 않고, 확장 시 마이그레이션으로 추가한다(열린 질문 참고).
- 서비스는 개발 서버 한 대에서 운영하며, 외부 공개 배포는 MVP 범위가 아니다. 내부망 또는 개인 환경에서 접근한다.
- 사용 언어는 한국어 단일이다.

## 4. 대상 사용자 및 페르소나

### 4.1 페르소나

**페르소나 A: 김민준 (32세, 개발자, 1인 가구)**
- 회사 근처 식당 10여 곳을 돌려 먹으며, 점심마다 "뭐 먹지"로 시간을 쓴다.
- 인스타그램·지인 추천으로 알게 된 식당은 메모앱에 흩어져 있어 잘 찾지 못한다.
- 니즈: 가고 싶은 곳을 한곳에 모으고, 최근에 간 곳은 빼고 뽑아주길 원한다.

**페르소나 B: 이수진 (28세, 마케터, 팀 막내)**
- 팀 점심 메뉴를 정하는 역할을 자주 맡는다. 의견이 갈리면 부담이 크다.
- 니즈: 후보 몇 곳에서 공정하게 하나를 뽑아주는 도구. MVP에서는 본인 목록으로 먼저 쓰고, 이후 팀 공유를 기대한다.

### 4.2 핵심 사용자 시나리오

| ID | 시나리오 | 흐름 |
|----|----------|------|
| S1 | 식당 저장 | 점심 후 마음에 든 식당을 등록한다: 이름, 카테고리, 가격대, 메모 입력 후 저장. |
| S2 | 가보고 싶은 곳 적립 | 추천받은 식당을 "가보고 싶음" 상태로 빠르게 등록한다(이름과 카테고리만). |
| S3 | 오늘의 추천 | 메인 화면에서 "한식, 1만원대" 조건을 켜고 [추천받기]를 누른다. 카드로 식당이 표시된다. |
| S4 | 다시 뽑기 | 마음에 들지 않으면 [다시 뽑기]를 누른다. 직전에 나온 식당은 연속으로 나오지 않는다. |
| S5 | 수락과 방문 처리 | [여기로 갈래요]를 누르면 오늘 날짜로 방문 기록이 생기고, 최근 N일 제외 조건에 반영된다. |
| S6 | 기록 확인 | 방문 기록 화면에서 최근 한 달간 어디를 갔는지 확인하고, 필요 시 기록을 삭제한다. |

## 5. 기능 요구사항

우선순위: **P0** = MVP 필수, **P1** = MVP 포함 권장, **P2** = 이후 개선.

### 5.1 식당 관리

| ID | 기능 | 설명 | 우선순위 |
|----|------|------|----------|
| FR-01 | 식당 등록 | 이름(필수), 카테고리(필수), 상태(필수) 외 선택 항목을 입력해 식당을 등록한다. | P0 |
| FR-02 | 식당 목록 조회 | 등록된 식당을 목록으로 보여준다. 기본 정렬은 최근 등록순이다. | P0 |
| FR-03 | 식당 상세 조회 | 식당의 모든 필드와 최근 방문 이력을 보여준다. | P0 |
| FR-04 | 식당 수정 | 모든 필드를 수정할 수 있다. | P0 |
| FR-05 | 식당 삭제 | 식당을 삭제한다. 삭제 전 확인창을 띄우고, 연결된 방문 기록도 함께 삭제한다. | P0 |
| FR-06 | 즐겨찾기 | 식당에 즐겨찾기 표시를 켜고 끌 수 있다. 목록에서 즐겨찾기만 모아 볼 수 있다. | P1 |
| FR-07 | 태그 | 식당에 자유 태그(예: 혼밥, 국물, 회식)를 여러 개 붙인다. 태그로 필터링한다. | P2 |

### 5.2 식당 정보 필드

| 필드 | 필수 | 설명 / 값 |
|------|------|-----------|
| 이름 | O | 1~100자 |
| 카테고리 | O | 한식 / 중식 / 일식 / 양식 / 분식 / 기타 |
| 상태 | O | `자주 감`(REGULAR) / `가보고 싶음`(WISHLIST). 기본값은 가보고 싶음 |

| 위치/주소 | X | 텍스트 (예: "역삼역 3번 출구 앞"). 지도 연동 없음 |
| 메모 | X | 추천 메뉴, 웨이팅 정보 등 자유 텍스트, 최대 1000자 |
| 즐겨찾기 | X | true/false, 기본 false |
| 태그 | X | 0개 이상 (P2) |

## 6. 데이터 모델

MariaDB 10.6 이상, 문자셋 `utf8mb4`, 콜레이션 `utf8mb4_unicode_ci`, 엔진 InnoDB를 사용한다. 스키마 DDL은 `db/` 디렉터리에서 관리한다.

### 6.1 restaurants

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 식별자 |
| name | VARCHAR(100) | NOT NULL | 식당 이름 |
| category | ENUM('KOREAN','CHINESE','JAPANESE','WESTERN','SNACK','ETC') | NOT NULL | 카테고리 |
| status | ENUM('REGULAR','WISHLIST') | NOT NULL, DEFAULT 'WISHLIST' | 자주 감 / 가보고 싶음 |
| price_level | TINYINT UNSIGNED | NULL, CHECK (price_level BETWEEN 1 AND 4) | 가격대 |
| location | VARCHAR(255) | NULL | 위치/주소 텍스트 |
| memo | TEXT | NULL | 메모 (앱에서 1000자 제한) |
| is_favorite | BOOLEAN | NOT NULL, DEFAULT FALSE | 즐겨찾기 |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 생성 시각 |
| updated_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 수정 시각 |

인덱스: `idx_restaurants_category_status (category, status)`, `idx_restaurants_name (name)`. 동일 이름 중복(지점 다름)은 허용하고 경고만 표시한다.

### 6.2 visits

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| id | BIGINT UNSIGNED | PK, AUTO_INCREMENT | 식별자 |
| restaurant_id | BIGINT UNSIGNED | NOT NULL, FK -> restaurants.id ON DELETE CASCADE | 방문한 식당 |
| visited_on | DATE | NOT NULL | 방문일 |
| source | ENUM('RECOMMENDATION','MANUAL') | NOT NULL, DEFAULT 'MANUAL' | 추천 수락인지 수동 입력인지 |
| note | VARCHAR(255) | NULL | 한 줄 메모 |
| created_at | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 생성 시각 |

인덱스: `idx_visits_restaurant_date (restaurant_id, visited_on DESC)`, `idx_visits_date (visited_on)`.
같은 식당의 같은 날 중복 방문은 허용한다(점심·저녁 가능).

### 6.3 tags / restaurant_tags (선택, P2)

| 테이블 | 컬럼 | 타입 | 제약 |
|--------|------|------|------|
| tags | id | BIGINT UNSIGNED | PK, AUTO_INCREMENT |
| tags | name | VARCHAR(30) | NOT NULL, UNIQUE |
| restaurant_tags | restaurant_id | BIGINT UNSIGNED | PK(복합), FK -> restaurants.id ON DELETE CASCADE |
| restaurant_tags | tag_id | BIGINT UNSIGNED | PK(복합), FK -> tags.id ON DELETE CASCADE |

### 6.4 관계

```
restaurants 1 ──< N visits
restaurants N ──< restaurant_tags >── N tags   (P2)
```

"마지막 방문일"은 별도 컬럼으로 저장하지 않고 `visits`에서 `MAX(visited_on)`으로 계산한다(정합성 우선, 데이터 규모가 작음).

## 7. API 명세 (초안)

- Base path: `/api/v1`, 형식: JSON, 문자셋 UTF-8
- 문서: FastAPI 자동 문서(`/docs`)를 개발 환경에서 제공한다.
- 오류 응답 공통 형식: `{"error": {"code": "NOT_FOUND", "message": "..."}}`
- 입력 검증은 Pydantic 스키마로 수행하며 실패 시 `422`를 반환한다.

### 7.1 엔드포인트

| 메서드 | 경로 | 설명 | 주요 파라미터 | 우선순위 |
|--------|------|------|---------------|----------|
| GET | `/api/v1/health` | 헬스체크. 앱 상태와 DB 연결 여부를 반환한다. | - | P0 |
| GET | `/api/v1/restaurants` | 식당 목록 조회 | query: `q`, `category`, `price_level`, `status`, `is_favorite`, `sort`, `limit`, `offset` | P0 |
| POST | `/api/v1/restaurants` | 식당 등록 | body: name, category, status, price_level, location, memo, is_favorite | P0 |
| GET | `/api/v1/restaurants/{id}` | 식당 상세 | path: id | P0 |
| PUT | `/api/v1/restaurants/{id}` | 식당 수정 | path: id, body: 등록과 동일 | P0 |
| DELETE | `/api/v1/restaurants/{id}` | 식당 삭제 (방문 기록 연쇄 삭제) | path: id | P0 |
| PATCH | `/api/v1/restaurants/{id}/favorite` | 즐겨찾기 토글 | body: `is_favorite` | P1 |
| GET | `/api/v1/recommendations/random` | 조건에 맞는 식당 무작위 1건 추천 | query: `category`, `price_level`, `status`, `exclude_recent_days`, `is_favorite`, `exclude_id` | P0 |
| POST | `/api/v1/visits` | 방문 기록 생성 (추천 수락 포함) | body: restaurant_id, visited_on(기본 오늘), source, note | P0 |
| GET | `/api/v1/visits` | 방문 기록 목록 | query: `restaurant_id`, `from`, `to`, `limit`, `offset` | P1 |
| DELETE | `/api/v1/visits/{id}` | 방문 기록 삭제 | path: id | P1 |
| GET | `/api/v1/tags` | 태그 목록 | - | P2 |

### 7.2 추천 API 상세

`GET /api/v1/recommendations/random`

| 파라미터 | 타입 | 기본값 | 설명 |
|----------|------|--------|------|
| category | string, 복수 가능 | 전체 | `KOREAN`, `CHINESE` 등. 반복 지정 시 OR (`?category=KOREAN&category=JAPANESE`) |
| price_level | int, 복수 가능 | 전체 | 1~4. 반복 지정 시 OR |
| status | string | 전체 | `REGULAR` 또는 `WISHLIST` |
| is_favorite | bool | 미적용 | true면 즐겨찾기만 |
| exclude_recent_days | int | 7 | 0~90. 최근 N일 내 방문한 식당 제외 |
| exclude_id | int | 없음 | 직전 추천 결과 제외 (다시 뽑기용) |

응답 200 예시:

```json
{
  "restaurant": {
    "id": 12,
    "name": "을지로 칼국수",
    "category": "KOREAN",
    "status": "REGULAR",
    "price_level": 1,
    "location": "을지로3가역 근처",
    "memo": "점심 웨이팅 15분",
    "is_favorite": true,
    "last_visited_on": "2026-09-30"
  },
  "candidate_count": 8
}
```

- 후보가 없으면 `404`와 `NO_CANDIDATES` 코드를 반환한다. 프론트엔드는 이를 안내 메시지로 표시한다.
- 추천 결과는 서버에 저장하지 않는다(추천은 상태 변경이 없는 GET). 수락 시점에 `POST /visits`로 기록한다.
- 선택 로직은 백엔드 서비스 계층에서 구현한다(필터링 후 `random.choice`, P2에서 가중 추첨).

## 9. 비기능 요구사항

| 구분 | 요구사항 |
|------|----------|
| 3티어 분리 | 프론트엔드, 백엔드, DB는 각각 별도 디렉터리(`frontend/`, `backend/`, `db/`)와 별도 프로세스로 구성한다. 계층 간 통신은 네트워크 프로토콜(HTTP, MariaDB 프로토콜)만 사용하고 파일·코드를 직접 공유하지 않는다. |
| 데이터 접근 경로 | 프론트엔드는 백엔드 REST API로만 데이터를 요청한다. DB 직접 접근은 금지한다. |
| 환경변수 | 주소·포트·접속 정보는 `.env`로 주입하고 하드코딩하지 않는다. `.env`는 커밋하지 않고 `.env.example`만 관리한다. |
| DB 접속정보 | 호스트, 포트, 사용자, 비밀번호, DB명은 백엔드 `.env`에만 둔다. 프론트엔드 번들에는 API 경로(`VITE_API_BASE_URL=/api/v1`)만 포함한다. 브라우저는 프론트엔드 서버의 `/api`로 요청하고, 프론트엔드 서버(Vite dev/preview 프록시)가 `API_PROXY_TARGET`의 백엔드로 전달한다. |
| CORS | 백엔드는 허용 Origin 목록을 `CORS_ALLOW_ORIGINS` 환경변수로 받아 해당 Origin만 허용한다. 와일드카드(`*`)는 사용하지 않는다. |
| 입력 검증 | 모든 입력은 Pydantic으로 타입·길이·범위·enum을 검증한다. DB 접근은 ORM(SQLAlchemy) 또는 바인딩 파라미터만 사용해 SQL 인젝션을 막는다. |
| 출력 안전 | 프론트엔드는 사용자 입력을 `textContent`/`createElement`로 렌더링하고, 사용자 데이터를 `innerHTML`에 넣지 않는다. |
| 응답시간 | 개발 서버 기준 목록·추천 API p95 300ms 이하, 헬스체크 50ms 이하. 식당 1,000건, 방문 10,000건 규모까지 보장한다. |
| 기본 보안 | DB 계정은 해당 DB 한정 최소 권한으로 만든다. 오류 응답에 스택트레이스·SQL을 노출하지 않는다. 로그에 비밀번호를 남기지 않는다. 의존성은 버전을 고정한다(백엔드는 `uv.lock`, 프론트엔드는 `package-lock.json` 커밋). |
| 신뢰성 | 백엔드 시작 시 DB 연결을 확인하고, 연결 실패는 `/health`에서 비정상으로 보고한다. DB 덤프를 주기적으로 백업한다(수동 스크립트). |
| 접근성 / 호환성 | 최신 Chrome, Safari, Edge와 모바일 브라우저를 지원한다. 키보드 조작과 `prefers-reduced-motion`을 고려한다. |
| 검증 | 단위 테스트는 작성하지 않는다(사용자 결정). 빌드 성공, 서버 기동, `curl`을 이용한 API 수동 확인, 브라우저 화면 수동 확인으로 검증한다. |

### 10.2 백엔드 내부 구조 (제안)

```
backend/app/
  main.py          # 앱 생성, CORS, 라우터 등록
  core/config.py   # 환경변수 로딩 (pydantic-settings)
  api/v1/          # 라우터 (restaurants, recommendations, visits, health)
  schemas/         # Pydantic 요청/응답 모델
  services/        # 추천 로직 등 서비스 로직
  repositories/    # DB 접근 (SQLAlchemy)
  models/          # ORM 모델
```

### 10.3 환경변수 (예시)

| 위치 | 변수 | 예시 |
|------|------|------|
| frontend/.env | `VITE_API_BASE_URL` | `/api/v1` (같은 origin 상대 경로) |
| frontend/.env | `API_PROXY_TARGET` | `http://127.0.0.1:8000` (Vite 서버 전용, 번들에 미포함) |
| backend/.env | `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | `127.0.0.1`, `3306`, ... |
| backend/.env | `CORS_ALLOW_ORIGINS` | `http://localhost:5173` |
| backend/.env | `APP_ENV`, `APP_PORT` | `dev`, `8000` |

### 10.4 향후 분리 방안
- **프론트엔드 분리**: 정적 빌드 결과물을 별도 웹서버 또는 CDN에 배포한다. 웹서버(Nginx 등)가 `/api`를 백엔드로 프록시하거나, `VITE_API_BASE_URL`을 백엔드 절대 주소로 바꾸고 백엔드 `CORS_ALLOW_ORIGINS`에 프론트엔드 Origin을 추가한다.
- **백엔드 분리**: 별도 서버에 컨테이너 또는 systemd 서비스로 배포한다. `DB_HOST`만 DB 서버 주소로 바꾼다. 역방향 프록시(Nginx)에서 `/api` 경로를 위임할 수 있다.
- **DB 분리**: 별도 서버 또는 매니지드 DB로 이전한다. 백엔드의 방화벽 허용 IP만 열고 TLS 접속을 적용한다. 스키마는 `db/` 마이그레이션으로 재현한다.
- 위 분리 모두 코드 변경 없이 환경변수와 배포 설정만으로 가능해야 한다.

### 10.5 실행 방식 (직접 실행, uv)

컨테이너나 systemd를 쓰지 않고, 각 계층 프로세스를 개발 서버에서 직접 실행한다. 백엔드의 Python 버전, 가상환경, 의존성은 **uv**로 관리한다. `pip`와 `requirements.txt`는 쓰지 않는다.

| 계층 | 준비 | 실행 |
|------|------|------|
| 데이터 | OS 패키지로 MariaDB 설치, `db/schema.sql`·`db/seed.sql` 적용 | OS 서비스로 기동 (`127.0.0.1:3306`) |
| 애플리케이션 | `cd backend && uv sync` | `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` (개발 시 `--reload`) |
| 프레젠테이션 | `cd frontend && npm install` | 개발: `npm run dev` (:5173) / 빌드 확인: `npm run build && npm run preview` |

- 백엔드 의존성 추가는 `uv add <패키지>`, 개발용 도구는 `uv add --dev <패키지>`로 한다.
- `backend/pyproject.toml`, `backend/uv.lock`, `backend/.python-version`을 커밋한다. `.venv/`는 커밋하지 않는다.
- 도구 실행도 `uv run`을 거친다.
- 실행 방법은 `README.md`에 계층별 명령으로 정리한다.

## 14. 열린 질문

사용자에게 확인이 필요한 사항이다. 답변 전까지는 괄호 안의 기본안으로 진행한다.

1. ~~사용 범위~~ → **확정: 단일 사용자(본인 혼자 사용)**
2. ~~접근 환경~~ → **확정: 내부망 사용, MVP에 인증 없음**
3. 점심만 대상인가, 저녁도 포함하는가? 끼니 구분(점심/저녁)이 방문 기록과 추천에 필요한가? (기본안: 구분 없음)
4. 카테고리 6종(한식·중식·일식·양식·분식·기타)과 가격대 4단계 구간이 적절한가? 카페·술집 등을 추가할 것인가?
5. 최근 방문 제외 기본값 7일이 적절한가?
6. 추천 수락 시 바로 방문 처리해도 되는가, 아니면 실제로 다녀온 뒤 확정하는 별도 단계가 필요한가? (기본안: 수락 즉시 방문 처리, 삭제 가능)
7. 식당 삭제는 완전 삭제(hard delete)로 충분한가, 보관(soft delete)이 필요한가? (기본안: 완전 삭제)
8. 태그와 가중치 추천을 MVP에 포함할 것인가, 이후로 미룰 것인가? (기본안: 이후)
9. ~~배포 방식~~ → **확정: 직접 실행, 백엔드는 uv 사용** (10.5 참고). 개발 서버 OS는 미정이다.
10. 기존에 모아 둔 식당 목록(메모앱, 엑셀 등)이 있어 초기 데이터 가져오기가 필요한가?
11. 디자인 방향(톤, 색상, 다크모드 필요 여부)에 선호가 있는가?
